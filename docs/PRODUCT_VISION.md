# GPS World Lap Time Counter — プロダクト・ゴール像（設計書）

> 目的: 「動くもの」から「販売できるプロダクト」へ。ロール分離・コース資産の階層管理・イベント参加フロー・課金モデルの**ゴール像**を明文化し、今後の作り込みの指針とする。
> 作成: 2026-08-03 / 次の実地検証: 2026-08-17 鈴鹿

---

## 0. 現状の資産（ここから作る）

2つの実装が並存している。**フルアプリを本命の土台**とし、単体HTML版は「サンプル/現場フォールバック」として残す。

| 実装 | 位置 | 役割 |
|---|---|---|
| **フルアプリ** | `frontend/`(React) + `backend/`(Express+Prisma) + Neon(PostgreSQL) | 本命。ロール・コース資産・イベントの基盤が**既に実装済み** |
| **単体HTML版** | `gps/index.html`（開発版）, `stable/`（富士実走の固定サンプル） | サーバー不要で確実に動く。デモ・現場保険 |

### フルアプリに既にあるもの（重要）
- `UserRole`: **DRIVER / ORGANIZER / ADMIN** ← 3ロール分離が既にある
- `Course`: country / state / sportCategories / courseType / コントロールライン / **createdBy(所有者)** / isPublic
- `CourseType`: CLOSED_CIRCUIT / PUBLIC_ROAD / FARM_ROAD / TRAIL / WATER / OTHER
- `SportCategory`: CAR / MOTORCYCLE / KART / BICYCLE_* / RUNNING_* / SKIING / SNOWBOARDING / BOAT / CANOE / OTHER
- `Event`: name / **eventCode(6桁)** / courseId / organizerId / 開催期間
- `Lap`: 計測記録

→ **あなたの構想（ロール分離・国→スポーツ→コースの階層・イベントID参加・GPSは運営が登録）は、スキーマ上ほぼ揃っている。** ゴールはゼロ実装ではなく「これらを繋いで権限で締める」こと。

## 1. ロールと権限（誰が何をできるか）

| ロール | GPS/コース登録 | イベント作成 | 計測して記録 | 想定ユーザー | 課金 |
|---|---|---|---|---|---|
| **ADMIN（あなた/統括）** | ✅ 全て | ✅ | ✅ | サービス提供者 | — |
| **ORGANIZER（運営者）** | △ 方針で選択（下記） | ✅ | ✅ | サーキット主催者・走行会運営 | 運営者向けプラン |
| **DRIVER（参加者）** | ❌ 不可 | ❌ | ✅ | 走行会参加者 | 参加者向けプラン |

**GPS/コース登録の方針（2026-08-03 決定）:**
- **採用: 案B（ORGANIZERも登録可 ＋ ADMIN承認）。** 運営者は自分のコースを登録できる（`createdBy`で所有）が、公開コース資産に載せる前に**ADMINが承認**する。スケール（運営者が各地のコースを足せる）と品質（統括が承認で担保）を両立。
- 承認前は「申請中」ステータス。承認済みは「検証済み」バッジ。
- **参加者(DRIVER)はGPS/コース登録UIを持たない**（イベントコードで入り、コースは自動セット）。現状の単体HTML版の「使用者が自分でGPS登録」は暫定運用で、プロダクト版では外す。

**参加者から見える範囲（2026-08-03 確認・現状維持でよい）:**
- 参加者は**自分のタイムは全て見られる**が、他人は**ランキングのベストラップのみ**閲覧可（毎ラップの他人データは見せない）。この方針を維持。

## 2. コース資産の階層（世界中のGPSラインを整理）

`Course` を階層で検索・登録できるようにする。DBには既に必要なフィールドがある。

```
国 (country)
 └ スポーツ種別 (sportCategories)
     └ コース種別 (courseType: 周回 / 片道 など)
         └ コース名 (name)  ← ここにGPSライン(コントロールライン)が紐づく
             ├ 周回モード: 1本のコントロールライン(A-B)
             └ 片道モード: スタートライン(A-B) + ゴールライン(GA-GB)  ※要スキーマ拡張
```

**必要な拡張:**
- 片道モード対応: `Course` にゴールライン(GA/GB)列と「計測タイプ(LAP/ONE_WAY)」を追加（単体HTML版で実装済みの概念をDBへ）。
- 検索UI: 国→スポーツ→コース種別→コース名 の絞り込み（`GET /api/circuits` は country/state フィルタ済み。階層UIを足す）。
- 公式コース資産（鈴鹿・富士など）はADMINが整備し「検証済み」バッジ。

## 3. イベント参加フロー（参加者は登録済みコースを使うだけ）

```
【運営(ORGANIZER/ADMIN)】
  1. コース資産から使うコースを選ぶ（GPSライン登録済み）
  2. イベント作成 → eventCode(6桁) と イベント名 が発行される
  3. 参加者にコードを配布

【参加者(DRIVER)】
  1. 参加者ページで イベントID(eventCode) または イベント名 で入る
  2. 自動で「そのイベントのコース＝GPSライン」が読み込まれる（自分で登録しない）
  3. 計測スタート → ラップ/区間を記録 → ランキングに反映
```

既に `Event.eventCode`・`EventLogin.tsx`・`EventDetail.tsx` がある。ゴールは「参加者導線からGPS登録を外し、コードで入ればライン自動セット」を完成させること。

## 3.5 記録の受け皿 と 運営モニター（2026-08-03 決定）

**決定: 記録の受け皿を Google スプレッドシート(GAS) → フルアプリの DB(Neon) に集約する。**
- 理由: Googleスプレッド方式は運営ごとにGoogleアカウント連携が必要で運用が重い。DB集約なら連携不要で、モニター・CSV・統括ページが自然に作れる。既存 `Lap` モデルが土台。
- 単体HTML版のGAS/スプレッド方式は「サンプル/現場フォールバック」として残すが、プロダクト版は `POST /api/laps`（既存）にラップを送りDBへ。堅牢送信（localStorageキュー＋再送）はそのまま踏襲。

**運営モニター（運営ページ内、2種を切替表示）:**
1. **リアルタイム通過モニター**（トランスポンダー風）: ラップが入った瞬間に一覧へ行追加（`No.26 安福 LAP5 1:39.8 ←new`）。現場のライブ監視向け。SSE/ポーリングで更新（既存の `stats/stream` SSEの考え方を流用）。
2. **集計・ランキング表**: ドライバー別ベスト・全周回一覧。事後の結果配布向け。

**エクスポート（Googleアカウント不要）:**
- **CSV / ZIP ダウンロード**、および印刷用ビュー。運営ページから記録内容（現行の記録項目＋ゼッケン/クラス等）をそのまま出力。
- 記録項目は現行踏襲（多少の変更は都度反映）。

## 3.7 多言語対応（i18n, 2026-08-03 決定）

**決定: まず日本語・英語・中国語・韓国語の4言語。i18nの仕組み（キー参照＋言語ファイル）を入れ、他言語（伊・仏など）は言語ファイル追加で拡張。**
- 実装: react-i18next 等。テキストは `t('key')` で参照し、`ja/en/zh/ko.json` に翻訳を分離。言語追加＝ファイル1個追加＋選択肢1行（コード変更なし）。
- **言語選択は最初の画面（ID/パスワード入力前）に置く** → 選んだ言語が以降ずっと適用。選択はブラウザ保存で次回も維持。
- **参加者・運営とも言語選択可**。統括(ADMIN)は英語＋日本語でOK。
- **タイム/LAP/BEST等の共通用語・数値は英語で固定（国際標準）**、UI説明・ボタン・メッセージを翻訳。運営/参加者向けに「英語表記＋カッコ書きで選択言語」を併記すると親切（例: `Best Lap（ベストラップ）`）。
- 注意: 仕組みは簡単だが**翻訳文の質**が要（特に中韓のモータースポーツ用語）。機械翻訳＋ネイティブチェック推奨。

## 3.8 PWA化（配布形態の決定, 2026-08-03）

**決定: PWA化を採用。** Webアプリに manifest＋Service Worker を足し、「ホーム画面に追加」でアプリ化・オフライン動作・全画面表示を得る。ストア審査不要・低コスト。
- オフライン: 参加者アプリは Service Worker でキャッシュ＋既存の未送信キュー（localStorage）を踏襲し、電波の弱いコースでも動く。
- iOSの画面ロック(5分)問題は PWA でも完全には消えない → 根絶が必要になれば将来ネイティブ化。

## 3.6 統括ページ（ADMIN管理画面, 2026-08-03 決定）

ADMIN（あなた）が**登録済みの全データを確認・変更・削除**できる管理画面。
- **アカウント管理**: 運営者(ORGANIZER)のID/パスワード、参加者(DRIVER)のID/パスワード、詳細情報の確認・変更・削除。
- **コース資産管理**: 国・スポーツ別・コース名・GPSライン・コース種別の追加/編集/削除、承認（申請中→検証済み）。
- **イベント管理**: イベントの確認・編集・削除。
- 原則「登録されているものは全て編集可能」。操作は監査ログを残す（将来）。

## 4. 販売 / 課金モデル（2本立て・2026-08-03 サブスク主軸で決定）

**決定: サブスク（継続課金）を主軸とする。** 理由: ①ラップタイマーは走行会のたびに継続利用する道具、②サーバー/DB(Neon)のランニングコストが毎月かかるため収入も継続型が収支安定。

| 対象 | 提供価値 | 課金（サブスク主軸） |
|---|---|---|
| **運営者向け** | イベント作成・参加者管理・ライブ順位モニター・CSV/印刷・コース登録(承認制) | **月額サブスク**（規模で段階）。主力。 |
| **参加者向け** | 走行会で自分のスマホが本格ラップタイマー＋テレメトリー | サブスクは重い層もいるため、**「運営がまとめて購入」or「イベント単位の都度課金」を併用**（ハイブリッド）。要詳細設計。 |

**販売時の権限の締め方（ゴール）:**
- 参加者アプリは**GPS/コース登録UIを持たない**。イベントコードで入るのみ。
- コース資産（世界中のGPSライン）は**運営/ADMIN管理**。これ自体がプロダクトの資産価値＝差別化。
- ライセンス/認証: ログイン必須化、ロールで機能ゲート、支払い状態で有効化（決済連携=Stripe等は将来Phase）。

**価格（2026-08-03 仮決定）:**
- 参加者: **300〜500円/月**（サブスク）。
- 運営者: **月額3,000円 or 都度2,000円 を選択制**。
- 収支概算（運営100・利用者1000, 利用者400円想定）: 収入 月30万＋40万＝**月70万**、コスト（DB $19＋ホスティング＋決済手数料3.6%）≈**月3万程度**。DBコストは収入の1%以下。→ 価格設定は成立。ホスティングと決済手数料の詰めが重要。

**DBランニングコスト試算（運営100・利用者1000）:**
- データ: 利用者1000×平均20ラップ×月4回=月8万ラップ、1ラップ≈200B → 月16MB／年200MB弱。**テレメトリー(GPS全点)はスマホ内保存でDBに乗らない**のが効く。
- Neon: Free(0.5GB,自動スリープあり)で数年分入るが、**商用は有料前提**。**Launch 約$19/月(≈3,000円, スリープなし)でこの規模は十分**。大規模化でScale($69〜)。
- 結論: **この規模ではDBは月$0〜$19。ボトルネックはDBでなくホスティング/決済手数料。**

## 5. 段階的ロードマップ（案）

```
Phase 0（済〜現在）: 単体HTML版で実働（富士検証OK）＋テレメトリー/片道/入力項目を追加中
Phase 1: フルアプリに「ロール認証＋イベントコード参加＋コース自動セット」を通す。
         参加者導線からGPS登録を外す。ラップ送信を DB(POST /api/laps) へ集約。
         単体HTML版の計測ロジック（アウトラップ/セッション/片道）をフルアプリへ移植。
Phase 2: コース資産の階層検索UI（国→スポーツ→種別→コース）＋片道モードのDB対応。
         ORGANIZERのコース登録＋ADMIN承認フロー。統括ページ（全データCRUD）。
Phase 3: 運営モニター（ライブ通過＋集計表）＋CSV/ZIP/印刷。テレメトリー(軌跡地図)をフルアプリへ。
Phase 4: PWA化（オフライン＋ホーム画面追加）。
Phase 5: 課金・ライセンス（運営サブスク＋参加者一括/都度）、決済連携。売れ行き次第でネイティブ化。
```

各Phaseで鈴鹿等の実地検証を挟む。単体HTML版は常にサンプル/フォールバックとして `stable/` に維持。

## 6. 決定事項（2026-08-03）と 残る検討

**決定済み:**
1. コース登録の権限 → **案B（ORGANIZERも登録可＋ADMIN承認）**。
2. 課金形態 → **サブスク主軸**（運営=月額、参加者=一括購入/都度課金の併用）。
3. 記録の受け皿 → **フルアプリDB(Neon)に集約**（GAS/スプレッドは廃止方向、単体HTML版のみ残す）。
4. 運営モニター → **ライブ通過モニター＋集計表の両方**、CSV/ZIP/印刷出力。
5. 統括ページ → ADMINが全データ（アカウント/コース/イベント/国・スポーツ・名前）を確認・変更・削除。
6. 参加者の閲覧範囲 → 自分は全タイム、他人はランキングのベストラップのみ（現状維持）。
7. 配布形態 → **PWA化を採用**（次フェーズ）。売れ行き次第でネイティブ化。
8. 価格 → 参加者 300〜500円/月、運営者 月額3,000円 or 都度2,000円 の選択制。
9. 多言語 → まず日英中韓4言語、i18nの仕組みで他言語は拡張可。言語選択はログイン前画面。
10. DBコスト → この規模で月$0〜$19。ボトルネックはDBでなくホスティング/決済手数料。

**残る検討:**
- 参加者向け課金の詳細（一括購入の単位・イベント都度課金の価格）。
- 決済連携（Stripe等）の導入時期・手数料の織り込み。
- ホスティング先の確定（Cloud Run無料枠→有料の閾値）。
- 単体HTML版の計測ロジック（アウトラップ/セッション/片道/テレメトリー）をフルアプリへ移植する順序。
- CSV/印刷の項目レイアウト（記録内容は現行踏襲＋微調整）。
- 各言語の翻訳文の用意（機械翻訳＋ネイティブチェック）。

## 付記: 設計の指針
- **既存スキーマ（role/course/event）を壊さず活かす**。あなたの構想と一致しているため、作り直しではなく統合。
- **単体HTML版で確立した実働ノウハウ**（堅牢送信・ライン幅・アウトラップ=LAP1・セッション・片道・テレメトリー）を、フルアプリ移植時の仕様書として使う。
- 販売を見据え、**権限（ロール）で機能をゲートする設計**を早めに骨格へ入れる。
